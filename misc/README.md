# Автономные инструменты проверки SWS/WAF

В каталоге находятся две отдельные программы на Go без внешних зависимостей и без импортов из основного проекта:

- `wafcheck` выполняет воспроизводимый набор HTTP-проверок WAF и сохраняет отчёт `wafcheck/v1`;
- `swslog` нормализует и агрегирует логи Smart Web Security, отдельно учитывает active/dry-run срабатывания и при необходимости сопоставляет их с отчётом `wafcheck`.

Обе программы работают только со стандартной библиотекой Go. `wafcheck` не знает устройство приложения, а `swslog` не требует SDK или CLI конкретного облака: первый управляется JSON-планом, второй читает уже выгруженный JSON из файла или stdin.

## Быстрая проверка

```bash
cd misc
go test -race ./...
go run ./wafcheck -help
go run ./swslog -input examples/sws-log.json
```

## `wafcheck`

Для первичной проверки одного маршрута можно использовать встроенную матрицу:

```bash
go run ./wafcheck \
  -target https://service.example.test \
  -path /api/check \
  -output waf-report.json
```

Она последовательно проверяет baseline, XSS, SQL injection, path traversal, сигнатуру сканера, метод `TRACE` и тело размером чуть больше 1 MiB. Встроенная матрица ожидает, что baseline будет разрешён, а остальные запросы заблокированы. Если приложение само возвращает `404`, `405` или иной неоднозначный ответ, используйте явный план.

Пример независимого плана находится в [examples/waf-plan.json](examples/waf-plan.json). Целевой адрес из него удобно переопределять флагом:

```bash
go run ./wafcheck \
  -plan examples/waf-plan.json \
  -target https://real-service.example \
  -parallel 2 \
  -output waf-report.json
```

Для A/B-проверки rule set'ов на лабораторном приложении подготовлена расширенная
матрица [examples/sws-lab-ruleset-comparison.json](examples/sws-lab-ruleset-comparison.json).
Она отдельно маркирует benign/benign-edge, семейства атак и общую политику
размера тела, чтобы блокировку по `size_limit` не приписывать сигнатурам WAF.

Каждый запрос получает одинаковый корреляционный идентификатор в `X-Request-ID` и `X-WAF-Test-ID`. Отчёт содержит URL тестового запроса, но не содержит его тело или отправленные заголовки. Ответ сохраняется только в виде безопасного набора диагностических заголовков; фрагмент тела по умолчанию отключён.

План поддерживает:

- произвольные HTTP-методы, пути, повторяющиеся query-параметры и заголовки;
- тела `raw`, `json`, `form`, `file`, `multipart` и генерируемое тело заданного размера;
- ожидания по решению `allow`, `block`, `captcha`, `unknown` или `any`;
- допустимые HTTP-статусы, обязательные и отсутствующие заголовки;
- настраиваемые статусы блокировки/CAPTCHA и origin-заголовок, позволяющий отличить ответ приложения от ответа WAF.

Решение определяется в следующем порядке: `X-Yandex-Captcha`, настроенные CAPTCHA-статусы, настроенные block-статусы, origin-маркер, затем успешный `2xx`. Остальные ответы считаются `unknown`, чтобы не принять обычный `404` приложения за блокировку WAF.

Коды завершения: `0` — все ожидания выполнены, `1` — есть несовпадения или ошибки запросов, `2` — ошибка конфигурации/ввода. Для просмотра итогового плана без отправки запросов есть `-print-plan`.

## `swslog`

Анализ сохранённой выгрузки:

```bash
go run ./swslog \
  -input sws-logs.json \
  -since 24h \
  -top 30 \
  -output sws-analysis.json
```

Потоковый ввод также поддерживается:

```bash
your-log-export-command --format json | go run ./swslog -input -
```

Допустимы JSON-массив, JSONL и объекты-обёртки с массивом в `entries`, `records`, `items` или `logs`. Нормализатор понимает как плоские поля наподобие `labels.action`, так и вложенные варианты `labels.action` и `smartwebsecurity.*`. Поля `dry_run_*` преобразуются в отдельные dry-run оценки, поэтому один исходный лог может дать две оценки — active и dry-run.

Отчёт включает:

- распределение actions/verdicts и active/dry-run;
- частоты security rules, WAF-сигнатур, суммы anomaly score и blocking-признаки;
- маршруты (без значений query-параметров), хосты, исключения и часовую шкалу;
- количество уникальных request ID и максимальный WAF score;
- dry-run запросы, которые были бы заблокированы, разрешённые запросы с WAF-сигнатурами и блокировки без сигнатур;
- клиентов в маскированном виде (`/24` для IPv4 и `/48` для IPv6) по умолчанию.

Полные IP включаются только явно через `-client-ids full`; полностью исключить их можно через `-client-ids omit`. Значения `matched_data_value`, тела и необработанные payload анализатор не выводит.

### Корреляция с тестами

```bash
go run ./swslog \
  -input sws-logs.json \
  -report waf-report.json \
  -request-id-prefix wafcheck- \
  -fail-on-missing \
  -fail-on-conflict
```

Для каждого кейса выводятся HTTP-решение, фактическое решение из логов, active/dry-run verdicts, сигнатуры и максимальный score. `missing` означает, что request ID из отчёта не найден; `conflict` — что сопоставимые HTTP- и log-решения различаются; `inconclusive` — что хотя бы одну сторону нельзя надёжно классифицировать. Для CI доступны `-fail-on-missing`, `-fail-on-conflict`, `-fail-on-inconclusive` и `-fail-on-empty`. Без fail-флагов анализатор возвращает `0`; ошибки формата/ввода возвращают `2`.

Если балансировщик заменяет клиентский `X-Request-ID`, экспорт логов должен включать `X-WAF-Test-ID` либо другой сохранённый корреляционный идентификатор. Для тестовой корреляции нормализатор сначала ищет `X-WAF-Test-ID`, затем стандартный ALB request ID и `X-Request-ID`; это не даёт подменённому балансировщиком ID скрыть явный marker теста.

Запускайте активную матрицу только против ресурсов, на тестирование которых у вас есть разрешение. По умолчанию запросы идут последовательно; увеличивайте `-parallel` с учётом лимитов сервиса.
